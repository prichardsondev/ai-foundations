Live Basement API Demo: From Data to Automation to Agents

This classroom demo uses a real public API from two Raspberry Pi sensor systems in Paul's basement. It shows how live data can support simple automation and how an agent-style system could add explanation, uncertainty, and human review.

1. Physical setup

Two small sensors report temperature and humidity from different parts of the basement.

Far-side sensor

One Raspberry Pi sensor is on the far side of the basement. It gives a baseline reading away from the pellet stove.

Near-stove sensor

Another Raspberry Pi sensor is near the pellet stove. If that area is much warmer than the far side, the stove may be running.

Simple API definition

An API is a way for one system to ask another system for data or an action. In this example, a browser, workflow, or AI tool can ask the basement API for current sensor readings.

2. API endpoints

Open these links during class to see the live API responses.

  • /api/health = system check
  • /api/temp = raw data from the far-side sensor
  • /api/all = combined API data from both sensors
  • /api/status = coded automation that estimates stove status

Live display note

This static course page links to the live API, but it does not fetch the data directly in the browser because the API does not currently send the CORS headers needed for cross-site browser fetch.

These examples show the shape of the data. The live values will change over time.

Coded automation: /api/status

{
  "difference_f": -0.3,
  "far_side_f": 64.0,
  "method": "coded_rules",
  "near_stove_f": 63.7,
  "stove_status": "LIKELY OFF",
  "time": "2026-05-18T15:44:14Z"
}

This endpoint applies fixed logic and returns a simple status. It is more than raw data, but it is still not a full agent.

4. Data, automation, and agents

The same API can support different levels of work.

Raw data

/api/temp returns one current sensor reading. It does not interpret the situation.

Combined data

/api/all returns both sensors together, which makes comparison easier.

Coded automation

/api/status applies fixed rules and returns a stove status such as LIKELY RUNNING or LIKELY OFF.

Agent-style interpretation

An agent-style system could read the data, explain uncertainty, compare readings over time if available, and suggest what a person should check next.

5. Why /api/status is automation, not a full agent

It is useful, but it follows fixed rules.

  • It follows the same coded rules each time.
  • It does not decide which tools to use.
  • It does not inspect history.
  • It does not explain uncertainty beyond the coded output.
  • It does not ask for human review.

6. What an agent version could add

An agent could turn data into a more useful explanation and next step.

  • Review the last hour or day of readings if history exists.
  • Compare stove behavior to time of day or weather.
  • Explain the result in plain English.
  • Flag uncertainty.
  • Suggest whether a human should check the stove.
  • Log a summary or prepare a report.
  • Ask before sending alerts or taking action.

7. In-class activity

Classify each example by what kind of system behavior it shows.

  • /api/health = system check
  • /api/temp = raw data
  • /api/all = combined API data
  • /api/status = coded automation
  • "Explain whether the stove is running and what you would check next" = agent-style reasoning

8. Codex prompts

Use these prompts to connect the API demo back to agent workspaces.

Prompt 1

Review https://basetemp.raspberrynode.com/ and its API endpoints. Do not write code yet. Explain what each endpoint does and classify each one as raw data, combined data, coded automation, or possible agent input.

Prompt 2

Using the live API data, explain in plain English whether the pellet stove appears to be running. Separate what the API proves from what you are inferring.

Prompt 3

Design a simple manager-friendly dashboard for this API. Keep it non-technical and focused on what a person should notice.

Prompt 4

Explain how this could become an agent-style system. Include tools, steps, actions, guardrails, and where human review should happen.

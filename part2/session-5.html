Part 2 - Section 5

Containers, Sandboxes, and Safe Agent Execution

Coding agents can run commands, install software, and change files. This lesson uses Docker to make those powers visible, then introduces stronger sandbox boundaries for agent work.

By the end of this lesson, you should be able to

  • Explain the difference between an image, a container, and a virtual machine.
  • Build, run, inspect, stop, and remove a basic container.
  • Explain how mounts, ports, networks, users, and secrets cross an isolation boundary.
  • Recognize dangerous Docker options and overly broad agent permissions.
  • Compare host execution, ordinary containers, and Docker Sandboxes.
  • Run an agent in an isolated clone and review its work before accepting it.

Start here: have an agent guide the lab

Open Codex or another coding agent in a new, empty class folder and paste this prompt. The agent must guide you one checkpoint at a time rather than performing an unattended setup.

This prompt changes your computer only with permission

Installing Docker and changing group membership are system-level actions. Read the proposed commands before approving them. Use a class machine or approved personal machine—not a production server or employer-managed computer without authorization.

Agent-first setup prompt

Act as my Docker and agent-sandbox lab guide. Teach me one numbered checkpoint
at a time. Explain each command in plain language, tell me exactly where to run
it, show the important expected output, and wait for me to confirm the result
before continuing.

Safety rules:
- Begin with read-only preflight checks. Do not install or change anything yet.
- Identify the operating system, version, CPU architecture, available memory,
  virtualization/KVM support, whether Docker is installed, and whether the
  current user can access Docker.
- Summarize what you found and whether ordinary Docker and Docker Sandboxes are
  supported. Ask for my approval before the first installation or system change.
- Use the current official Docker instructions for my exact operating system.
  Do not guess package commands for a different Linux distribution.
- Explain that membership in the docker group is effectively high privilege
  before proposing that change. Do not make the change without my approval.
- Never use --privileged. Never mount /, my entire home directory,
  /var/run/docker.sock, SSH keys, cloud credentials, browser data, or .env files.
- Do not disable security controls to make a failed command work.
- Use only a new folder named docker-safety-lab for writable mount experiments.
- Do not delete images, containers, volumes, or files that this lab did not create.
- If a command fails, explain why and repair only the current checkpoint.

Guide me through this sequence:
1. Perform and explain the read-only compatibility preflight.
2. With my approval, install or start ordinary Docker using official instructions.
3. Verify it with docker version, docker info, and docker run --rm hello-world.
4. Teach image versus container with docker image ls and docker container ls -a.
5. Demonstrate that a file created only inside a disposable container does not
   become a host file.
6. Create ~/projects/docker-safety-lab/host-data and demonstrate that mounting
   only that folder allows the container to change that folder. Show the exact
   host file before and after.
7. Run a small web container on an explicitly published localhost port, test it,
   stop it, and confirm the port closes.
8. Run a disposable Alpine container with --read-only, --network none,
   --cap-drop ALL, --security-opt no-new-privileges, and a non-root user. Help me
   observe which actions are blocked.
9. Explain why --privileged, mounting the host Docker socket, mounting broad host
   directories, running as root, and copying secrets into images increase risk.
10. If and only if this machine meets the current Docker Sandboxes requirements,
    guide me through installing the current sbx CLI with official instructions.
    Otherwise, stop that installation and explain what requirement is missing.
11. In a safe Git practice repository, launch Codex with sbx in --clone mode,
    inspect the active network policy, ask the agent to make one harmless change
    and test it, then exit the sandbox.
12. On the host, fetch the sandbox Git remote, inspect its log and diff, and do
    not merge the work. Explain why review is still required after isolation.
13. Remove only the lab container and sandbox resources we created, then help me
    summarize container isolation, sandbox isolation, permissions, blast radius,
    secrets, network policy, and human review.

Do not skip the preflight, mount demonstration, restricted-container test,
workspace review, or cleanup. Do not describe a container as a perfect security
boundary. Make me predict what each experiment will allow before we run it.

1. Why this lesson follows agents

The more an AI system can do, the more carefully we must define where it can act.

chatbot:  produces text
agent:    produces text + reads files + runs commands + uses tools

more capability
  -> more possible benefit
  -> larger possible mistake
  -> stronger need for boundaries and review

The goal is not “make the agent safe”

No single setting removes every risk. The goal is to reduce the blast radius: limit the files, credentials, networks, tools, and machines an error or compromised dependency could affect.

2. Docker in plain language

Docker packages an application with the environment it needs and runs it in an isolated process space.

Image

A read-only packaged blueprint containing the application, runtime, libraries, and default instructions.

Container

A running instance of an image. It has an isolated process view and a writable container layer that can be discarded.

Dockerfile

A text file describing how to build an image. Because it is code, it can be reviewed, versioned, and rebuilt.

ApproachKernelTypical strengthTypical cost
Host processHost kernelNo added isolationLowest overhead
ContainerShares host kernelProcess and resource isolationLow overhead
Virtual machineSeparate guest kernelHypervisor boundaryMore memory and storage

3. Isolation has deliberate openings

A useful container often needs selected ways to communicate with the host or outside world. Each opening should be narrow and intentional.

OpeningWhat it enablesQuestion to ask
PortLets the host or network reach a container service.Which interface and exact port need exposure?
Bind mountGives the container access to a host path.Can it be narrower or read-only?
VolumePreserves data outside a disposable container layer.What data persists and who can read it?
NetworkAllows communication with other systems.Does this task need any network access?
Environment or secretSupplies configuration or credentials.Could the value leak through logs, files, or child processes?

The mount is the lesson

A container cannot modify an arbitrary host folder unless it is given a path to it. Once a writable folder is mounted, changes inside that path are real host changes. Isolation ends where you deliberately create a bridge.

4. The ordinary Docker lab

The agent prompt provides the full guided sequence. These are the major checkpoints you should observe.

Installation and health

  • Detect the operating system before choosing instructions.
  • Install from Docker's official repository or supported desktop application.
  • Run docker version and docker info.
  • Run the disposable hello-world test.

Lifecycle

  • Pull or build an image.
  • Create and run a container.
  • Inspect processes, logs, and published ports.
  • Stop and remove only class resources.

Boundary experiments

  • Compare a container-only file with a mounted host file.
  • Publish one local port and confirm when it closes.
  • Run with no network.
  • Run as a non-root user with a read-only filesystem.

Evidence to save

  • The exact commands you approved.
  • Which files appeared on the host.
  • Which restricted actions failed.
  • What remained after cleanup.

5. Dangerous shortcuts to recognize

These options can erase much of the protection students think a container provides.

ShortcutWhy it is riskySafer direction
--privilegedGrants extensive device and kernel capabilities.Add only the specific capability that is required.
Mounting / or the whole home folderExposes broad host data to reading, modification, or deletion.Mount one dedicated folder, preferably read-only.
Mounting /var/run/docker.sockLets the container control the host Docker daemon and create highly privileged workloads.Do not expose the host daemon to an untrusted agent.
Running everything as rootIncreases what a compromised process can do inside the container and through exposed resources.Use a non-root user and drop unnecessary capabilities.
Baking secrets into an imageSecrets can remain in image layers and registries.Provide narrowly scoped secrets at runtime.

6. From containers to Docker Sandboxes

Docker Sandboxes are designed for autonomous coding agents that need to run tools without receiving equivalent control over the host.

Where the agent runsImportant boundaryWhat still needs attention
Directly on the hostNo additional execution boundaryEverything available to the current user
Ordinary containerContainer namespaces sharing the host kernelMounts, host Docker socket, capabilities, secrets, and network
Docker Sandbox, direct workspaceSeparate microVM, kernel, network, and Docker daemonThe real workspace is still writable by the agent
Docker Sandbox, clone modeMicroVM plus a private Git cloneReadable repository contents, allowed network, and review of proposed changes

Use clone mode for the class demonstration

Direct mode allows the agent to edit the host working tree immediately. Clone mode mounts the host repository read-only and gives the agent a private clone. Students fetch and review the sandbox branch before accepting anything.

7. Docker Sandbox compatibility checkpoint

Do not assume that every machine capable of running ordinary Docker can run Docker Sandboxes.

  • macOS: Apple silicon with macOS Sonoma 14 or later.
  • Windows: Windows 11 on 64-bit Intel or AMD with Windows Hypervisor Platform.
  • Linux: Ubuntu 24.04 or later on x86-64 or ARM64, with KVM virtualization enabled and the user permitted to access KVM.

A Raspberry Pi running Raspberry Pi OS is not the same supported target as Ubuntu 24.04. Use the agent's preflight result instead of forcing installation by disabling checks.

8. The sandbox review workflow

The sandbox limits execution. Git provides the controlled path for proposed work to leave it.

safe practice Git repository
  -> sbx run --clone --name safe-agent codex
  -> agent changes and tests its private clone
  -> exit agent
  -> git fetch sandbox-safe-agent
  -> inspect log and diff on the host
  -> accept, revise, or reject
  -> remove the sandbox when finished

Isolation does not replace review

A sandbox can prevent an agent from reaching much of the host while it works. It cannot prove that the resulting code is correct, secure, maintainable, or appropriate to merge.

9. Check your understanding

Use the class experiments—not memorized definitions—to answer these questions.

  1. What is the difference between an image and a container?
  2. Which experiment proved that a bind mount crosses the container boundary?
  3. Why is mounting the host Docker socket especially dangerous?
  4. Which restrictions did the hardened disposable container demonstrate?
  5. Why is a Docker Sandbox stronger than an ordinary container for an autonomous agent?
  6. What can an agent still affect in direct workspace mode?
  7. What does clone mode change?
  8. Why must you still inspect the Git diff?

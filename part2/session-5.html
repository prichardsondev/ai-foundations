Docker, Containers, and Agent Sandboxes

Learn the basic idea first. Then use an AI agent to guide a small, permission-aware experiment. Run the Docker activities on a Raspberry Pi 5, then explore Docker Sandboxes on a supported Linux computer or Mac.

The one sentence to remember

A sandbox can reduce an agent’s blast radius, but it cannot make the agent’s work correct or safe. We still control access and review the result.

Docker

1. Docker overview

Docker packages an application and its environment, then runs it as an isolated process on the host computer.

Image = packaged blueprint

The application, runtime, libraries, and starting instruction packaged together.

Container = running copy

A process created from an image with a separated view of files and processes.

Dockerfile = build recipe

A short text file that tells Docker how to assemble an image.

Virtual machine = another computer

A VM has its own operating-system kernel. A normal container shares the host kernel, so it is generally smaller and faster to start.

Port mapping: HOST:CONTAINER

In -p 80:3000, traffic sent to port 80 on the Raspberry Pi is forwarded to port 3000 inside the container. The number on the left is the host port; the number on the right is the port where the app listens in the container.

Our lab uses -p 127.0.0.1:3000:3000: only the Pi itself can connect, using host port 3000, and Docker forwards that traffic to container port 3000. Without 127.0.0.1, the published port may also be reachable by other devices on the network.

Volumes keep selected data

A container’s writable files normally disappear when that container is removed. A Docker-managed named volume keeps selected data for later containers. A bind mount exposes a real host file or folder inside the container.

Volumes are useful for databases and other persistent data. Bind mounts are useful for source code, but they also weaken the boundary: a process in the container may read or change the mounted host files.

OpeningWhat it allowsQuestion to ask
PortReach a service in the containerWhich exact port and interface?
Volume or mountKeep data or reach a real host folderIs persistence needed, and can access be narrow or read-only?
NetworkReach outside systemsDoes this task need a network?
CredentialAct on an outside serviceHow narrow and temporary can it be?

Useful boundary, not a perfect wall

A container shares the Raspberry Pi’s kernel and can affect anything deliberately exposed to it. Do not use --privileged for an untrusted agent or mount the whole computer, home folder, SSH keys, .env files, browser data, or the host Docker socket.

Raspberry Pi 5

2. Agent prompt: check Docker setup

Paste this into Codex or Claude on the Pi. It starts with evidence, avoids unnecessary reinstalling, and asks before making changes.

Help me verify that this Raspberry Pi is ready for today's Docker lab.

Goal:
- Confirm the operating system, CPU architecture, available disk space,
  Docker version, Docker service status, and whether Docker can run a test image.

Instructions:
- Begin with read-only checks and explain the important result in plain language.
- Do not reinstall Docker if it is already working.
- Use sudo for Docker commands in this class.
- If Docker is missing or broken, explain what you found and ask before changing
  anything. Use the current official Docker instructions for this exact version
  of Raspberry Pi OS; do not use an unexamined curl-pipe-shell installer.
- Do not add me to the docker group. Explain that membership gives root-level
  power through the Docker daemon if that option comes up.
- Do not remove existing images, containers, volumes, files, or packages.
- Verify the final setup with docker version, docker info, and a disposable
  hello-world container.
- Stop when Docker is verified or when help is required. Give me a
  short summary of the evidence.

What success looks like

The successful result is not merely “the agent says it worked.” Look for Docker client and server information plus the hello-world confirmation.

Raspberry Pi 5

3. Agent prompt: run the Docker experiments

The agent guides one checkpoint at a time. Predict, observe, and explain rather than watching unattended commands scroll past.

Guide me through a short Docker lab one checkpoint at a time. At each
checkpoint, explain the command, ask me to predict the result, run only the
commands for that checkpoint, show the important evidence, and wait for my
confirmation before continuing.

Use sudo for Docker commands. Work only in:
~/projects/docker-safety-lab

Checkpoints:
1. Use docker image ls and docker container ls -a to reinforce the difference
   between an image and a container.
2. Start a disposable interactive alpine:3.22 container. Create and read
   /class-note.txt inside it, exit, and prove that /class-note.txt was not
   created on the Raspberry Pi.
3. Inspect node-app/server.js and node-app/Dockerfile. Explain each Dockerfile
   instruction in plain language without changing either file.
4. Build the image as foundations-node:1.
5. Run it as foundations-web with --rm and publish container port 3000 only to
   127.0.0.1:3000 on the Pi.
6. Show the running container and its logs, then use curl to confirm the page
   says "Hello from a Pi container!"
7. Stop foundations-web and prove that the local page is no longer reachable.
8. Summarize what crossed the boundary: the published port did; the disposable
   container file did not.

Safety rules:
- Never use --privileged.
- Do not create mounts or expose the Docker socket.
- Do not access secrets, SSH keys, browser data, or files outside the lab folder.
- Do not use broad cleanup or prune commands.
- If a checkpoint fails, diagnose only that checkpoint and ask before making a
  system change.
What the prepared Node example contains

server.js

const http = require("node:http");

const server = http.createServer((request, response) => {
  response.writeHead(200, { "Content-Type": "text/plain" });
  response.end("Hello from a Pi container!\n");
});

server.listen(3000, "0.0.0.0");

Dockerfile

FROM node:22-alpine
WORKDIR /app
COPY --chown=node:node server.js .
USER node
EXPOSE 3000
CMD ["node", "server.js"]

Supported Linux laptop or Mac

4. Docker Sandboxes overview

Docker Sandboxes are a separate tool and do not require Docker Desktop or Docker Engine. Each sandbox is a lightweight microVM with its own kernel, filesystem, network, and Docker daemon.

Agent locationUseful boundaryWhat still needs review
On the hostNo added execution boundaryEverything the user can reach
Ordinary containerContainer isolationMounts, shared kernel, network, and credentials
Sandbox direct modeSeparate microVMThe agent edits the real project immediately
Sandbox clone modeMicroVM plus private Git cloneProposed code, allowed network, and readable project content

Use clone mode for the demonstration

Direct mode shares the project read-write by default. Clone mode mounts the host repository read-only and gives the agent a private Git clone. The work reaches the host only when we deliberately fetch it for review.

Supported Linux laptop or Mac

5. Agent prompt: check Sandbox setup

Use this read-only readiness check before attempting the Sandbox experiment. Installation and sign-in are separate setup tasks.

Check whether this computer is ready for the Docker Sandbox
experiment. Determine the operating system before choosing any checks.
Do not install, update, sign in, or change configuration.

Verify and explain:
- On Linux: Ubuntu 24.04 or later, x86_64 or aarch64, a loaded KVM module,
  access to /dev/kvm, and current-user membership in the kvm group
- On macOS: Apple silicon and macOS Sonoma 14 or later
- sbx version and diagnostic result
- Docker sign-in status without displaying credentials or tokens
- the active sbx network policy
- that ~/projects/safe-agent-practice is a clean Git repository on main
- that the repository contains no .env file, credentials, personal files, or
  uncommitted work

The planned sandbox name is foundations-agent and the demonstration must use
clone mode. Report PASS or NEEDS ATTENTION for each item. Stop after
the report; do not launch the sandbox.

6. Agent prompt: run the Sandbox experiment

Launch the sandbox from the Linux laptop or Mac, then paste the second prompt into Codex running inside it.

A. Launch from the host computer

cd ~/projects/safe-agent-practice
git status --short
sbx policy ls
sbx run --clone --name foundations-agent codex

B. Paste inside the sandboxed Codex session

Demonstrate this sandbox boundary using only the current practice repository.

1. Show the current directory and Git status.
2. Explain which parts of the host this clone-mode sandbox can and cannot reach.
3. Create a branch named lesson/sandbox-review.
4. Add this sentence to README.md:
   "Sandboxes reduce risk, but they do not replace human review."
5. Show the diff and commit the change with a clear commit message.
6. Report the branch name and commit ID, then stop. Do not push, merge, access
   other files, add credentials, or change the network policy.

C. Exit and review from the host computer

git status --short
git fetch sandbox-foundations-agent
git log --oneline sandbox-foundations-agent/lesson/sandbox-review
git diff main..sandbox-foundations-agent/lesson/sandbox-review

sbx rm foundations-agent

The host working tree should remain unchanged. Do not merge during the demonstration. Fetching exposes a proposal for review; it does not prove the change is correct.

7. Two-minute recap

  1. An image is a packaged blueprint; a container is a running copy.
  2. A normal container shares the host kernel; a Docker Sandbox provides a separate microVM kernel.
  3. Ports, volumes, mounts, networks, workspaces, and credentials are intentional openings.
  4. Narrower access reduces the blast radius.
  5. The agent performs the experiment, but the human still approves changes and reviews evidence.

Setup and reuse checklist

Use this checklist when preparing the lesson for yourself, a class, or colleagues.

  • Install and verify Docker Engine on each Raspberry Pi 5 that will run the lab.
  • Place the prepared docker-safety-lab/node-app folder at ~/projects/docker-safety-lab/node-app on each Pi.
  • Pull hello-world, alpine:3.22, and node:22-alpine before a timed group session.
  • Run both Raspberry Pi prompts once and confirm port 3000 is available.
  • Prefer the Linux laptop: confirm Ubuntu 24.04+, 64-bit architecture, KVM support, /dev/kvm access, and membership in the kvm group.
  • If using a Mac instead, confirm Apple silicon and macOS 14 or later.
  • On the Sandbox host, confirm sbx login, Codex authentication, Balanced network policy, and clone mode.
  • Create safe-agent-practice as a clean Git repository on main with only a README and no secrets.
  • If you are leading a group, run the complete Sandbox experiment once and keep screenshots as a fallback.
